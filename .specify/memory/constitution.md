# AIPPO Constitution

AI初心者向けハンズオン学習アプリ **AIPPO（アイッポ）** の開発憲章。
本ドキュメントは、すべての spec / plan / tasks / 実装に優先する。

AIチューターの名前は **ポー**。

## Core Principles

### I. 初心者の「迷わなさ」が最優先 (NON-NEGOTIABLE)

対象ユーザーは「AIに興味はあるが、何に使えばよいか分からない非IT人材」である。
すべての機能は、この人が **次に何をすればよいか一目で分かる** ことを最優先に設計する。

- 画面上に、ユーザーが次に取るべき行動は常に **1つだけ** 提示する
- 専門用語（プロンプト、トークン、モデル、API、コンテキスト等）を UI に露出しない
  - どうしても必要な場合は、初出時に1文で言い換えを添える
- 自由入力を初期状態で要求しない。まず選択肢または穴埋め形式を提示する
- 「キャラクターがかわいいか」より「ユーザーが迷わないか」を優先する
  （AIPPO 開発概要 §17）

**適合の判定**: 新しい画面・状態を追加する PR は、その画面での「次の行動」が
何であるかを spec に1文で書けなければマージしない。

### II. MVPスコープの固定 (NON-NEGOTIABLE)

将来構想（個人用教材、ベンダー別コース、AIビジネス情報、法人研修、AI導入支援）は
`docs/business-plan.md` に記載するが、**MVPの実装スコープには入れない**。

MVPで検証するのは次の6点のみ:

1. AIの使い道を発見できるか
2. 一人でAIを操作できるか
3. 自分の成果物を完成できるか
4. 7日以内にもう一度AIを使うか
5. 次の内容も学びたいと思うか
6. 有料で利用するか

スコープ外と明示するもの（AIPPO 開発概要 §11）:
ネイティブアプリ / 複数キャラクター / Live2D / 3D / 音声会話 /
高度なゲーミフィケーション / ランキング / コミュニティ / 法人管理画面 /
資格制度 / 多言語 / 高度なAI自動採点 / ベンダー別コース /
自由な教材生成 / 決済機能。

**まず1レッスンを最後まで完成させる。** 最初から大規模な学習SaaSを作らない。

**適合の判定**: 上記6点の検証に寄与しない機能を含む spec は、Deferred セクションへ移す。

### III. 学習フローはアプリが持ち、ポーは補助に徹する

レッスンの進行は決定論的な状態機械（アプリ側）が所有する。
LLM が自由に学習フローを決めてはいけない（AIPPO 開発概要 §9）。

- 状態遷移は許可された遷移表に基づいてのみ行う。不正遷移は無視して現状態を維持する
- ポーの応答は固定スキーマ（`message` / `emotion` / `action` / `hint_level` /
  `completed`）に必ず適合させる。適合しない場合はフォールバック文言に置き換える
- API レスポンスの `action` は表示のヒントであり、**遷移の実行権を持たない**
- AI障害・タイムアウト時も、レッスンは必ず前に進める（固定ヒントで代替する）

ポーが担当するのは、現在の状態に応じた次の内容だけ:
短い説明 / ユーザー入力へのフィードバック / ヒント / 改善点 /
安全上の注意 / 次の操作の案内。

**適合の判定**: AI API を全面停止させた状態でレッスンを完走できることを、
統合テストで担保する。

### IV. AIを使う部分と使わない部分を分ける

コスト・レイテンシ・出力の不安定さを抑えるため、文言の出所を明確に二分する。

| 固定文（AIを使わない） | AI生成 |
| --- | --- |
| レッスン開始・完了メッセージ | ユーザー入力へのフィードバック |
| ボタン説明・次の操作案内 | AI回答の改善点 |
| 安全上の注意 | ユーザーに合わせた例示 |
| エラー表示・フォールバック | 自由入力課題へのヒント |
| 診断の質問文 | |

固定文は `frontend/src/content/` 配下のデータとして一元管理し、
コンポーネント内にハードコードしない。

**ポーは一度に複数の改善点を伝えず、最も重要な一つだけを伝える**（§8）。

ヒントの段階（§8）:

| level | 内容 |
| --- | --- |
| 0 | ヒントなし |
| 1 | 考える方向を示す |
| 2 | 選択肢や穴埋め形式を示す |
| 3 | 具体例を示す |

`hint_level` はサーバー側が `attempt_count` から決める。AIの自己申告は採用しない。
**1回目で正解そのものを提示しない。**

### V. 検証可能であること（テストとログ）

- 状態機械（reducer）とシリアライザは単体テストを必須とする
- AI プロバイダ呼び出しは必ずサービスクラスへ分離し、テストではモックする
- レッスン1本の通し操作を Playwright の E2E テストで担保する（AIはスタブ応答）
- ユーザー操作は学習イベントとして記録する。MVPの検証項目6点に直接対応する
  イベントのみを定義する
- **AI API 利用料を記録する**（`model_name` / `token_usage`）
- **1セッションあたりのAI実行回数に上限を設ける**。無制限だと利用料が青天井になる

**適合の判定**: reducer・serializer・API・E2E のいずれかに触れる変更は、
対応するテストの追加または更新を伴う。

### VI. 個人データは最小限しか集めない

- 収集するのは「学習に必要な入力」と「MVP検証に必要なイベント」のみ
- **操作ログ（LearningEvent）に入力本文を保存しない。** 文字数のみ記録する。
  本文は Attempt 側に置き、ログとコンテンツを分離する
- MVP は認証を持たず、匿名セッションキー（HttpOnly Cookie）で識別する
- 個人を特定できる情報をログ・エラートラッキングへ出力しない
- 外部AIプロバイダへ送るペイロードは、レッスンに必要な最小フィールドに限定する
- 個人情報・機密情報の入力に対しては、ポーが `warning` 状態で注意する

## Technology Constraints

初期スタックを次に固定する。逸脱は plan.md の Complexity Tracking で正当化を要する。

- **Backend**: Python 3.12 / Django 5 / Django REST Framework / PostgreSQL（開発は SQLite 可）
- **Frontend**: React 18 / TypeScript 5 / Vite / Tailwind CSS
- **Test**: pytest + pytest-django（backend） / Vitest + Testing Library（frontend） / Playwright（E2E）
- **AI**: プロバイダ非依存のインターフェースを定義し、実装を差し替え可能にする。
  **MVPで複数プロバイダを実装する必要はない**
- **i18n**: UI文言は日本語を第一言語とする。文言はコードから分離する

追加の制約:

- AIプロバイダを各画面から直接呼ばず、バックエンドのサービスクラスを通す
- AIプロバイダ固有の型・SDKをドメイン層・ビュー層へ漏らさない
- レッスン内容を React コンポーネントへ直接ハードコードしすぎない。
  教材は JSON またはデータベースで管理できる構造にする

## Development Workflow

本プロジェクトは Spec-Driven Development（GitHub Spec Kit）で進める。

1. `/speckit-constitution` — 原則の更新（本ファイル）
2. `/speckit-specify` — 仕様（何を・なぜ）。実装手段を書かない
3. `/speckit-clarify` — 曖昧点の解消（任意だが plan 前に推奨）
4. `/speckit-plan` — 実装計画（どう作るか）。技術選定はここで行う
5. `/speckit-tasks` — タスク分解。User Story 単位で独立して完了できること
6. `/speckit-analyze` — 成果物間の整合性チェック（任意）
7. `/speckit-implement` — 実装

ルール:

- `specs/` の成果物を経ずに機能実装を始めない
- 1つの User Story は、それ単体で価値を届けられる粒度にする
- spec に `[NEEDS CLARIFICATION]` が残る状態で plan へ進まない
- 憲章に反する実装は、plan.md の Complexity Tracking に理由と代替案を明記する
- **実装を開始する前に、設計と影響範囲を提示する**

## Governance

- 本憲章はすべての開発プラクティスに優先する
- 改訂は PR で行い、変更理由と影響範囲（既存 spec への波及）を記載する
- バージョニングは semver に従う
  - MAJOR: 原則の削除・後方非互換な再定義
  - MINOR: 原則やセクションの追加、実質的な拡張
  - PATCH: 表現の明確化・誤字修正
- すべての PR は、本憲章の NON-NEGOTIABLE 原則（I・II）への適合を確認する
