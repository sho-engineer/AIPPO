# 運用手順

公開したあとに「やっていないと困ること」をまとめてある。
機能を足す作業と違って、運用の抜けは**何も起きていないように見える**のが
やっかいなところ。バックアップは取れていないことに気づくのが復旧のときで、
定期削除は動いていないことに気づくのが問い合わせのときになる。

だからこの文書は、手順だけでなく **なぜ要るか** を並べて書く。
理由が分からない手順は、忙しいときに真っ先に飛ばされる。

対象は Vercel（画面 + API）と Neon（PostgreSQL）の構成。
配置そのものの手順は [deploy-vercel.md](./deploy-vercel.md) にある。

---

## 1. データベースのバックアップと復旧

### なぜ要るか

消えるのは学習者の記録で、こちらの都合では作り直せない。
そして消え方は「サーバーが壊れる」だけではない。むしろ多いのは

- 移行（migration）を当て間違えて、列ごと落とした
- 管理画面から選択削除で、意図より広く消した
- 接続先を取り違えて、本番に開発用の seed を流した

いずれも**こちらの操作**で起きる。壊れてから気づくまでに時間が空くので、
「直前の状態に戻す」手段が無いと、その間の記録がまとめて消える。

### 取り方（Neon）

Neon には**復元ポイント**（point-in-time restore）があり、
保持期間のあいだの任意の時刻へブランチを作れる。まずここを確認する。

1. Neon のダッシュボード → 対象プロジェクト → **Settings → Restore**
2. **History retention** を確認する。無料プランは既定で 6 時間ほどしかない。
   気づくまでの時間を考えると短すぎるので、**最低でも 7 日**へ伸ばす
   （伸ばせないプランなら、下の手動ダンプが本命になる）

これとは別に、**手元に落とせるダンプ**も取っておく。
Neon 側のアカウントごと失う事故（支払い停止、誤削除）は、
Neon の中の復元ポイントでは救えない。

```bash
# 接続文字列は Neon の Connection Details から。-Fc は圧縮形式
pg_dump "$DATABASE_URL" -Fc -f "aippo-$(date +%Y%m%d).dump"
```

週に1回、手元か別のクラウドストレージへ置く。
学習者数が数百のあいだはこれで足りる（ダンプは数MB程度）。

### 戻し方

```bash
# 空のデータベースへ戻す。既存へ上書きしない
createdb aippo_restore
pg_restore -d aippo_restore --no-owner "aippo-20260819.dump"
```

Neon の復元ポイントから戻すときは、**本番のブランチを直接巻き戻さない**。
別ブランチとして復元し、中身を確かめてから接続先を切り替える。
巻き戻しは、それ自体が取り消せない操作になる。

### 一度は必ず試すこと

**復旧を一度も試していない手順は、無いのと同じ。**

これは言葉のあやではなく、実際に次のようなことが起きる。

- ダンプは取れていたが、`pg_restore` が拡張機能の不足で止まる
- 戻したが、`django_migrations` の中身が合わずアプリが起動しない
- 手順書に書いた接続文字列が古く、そもそも繋がらない

どれも本番が落ちている最中に見つけたい種類のものではない。
公開前に一度、**手順書だけを見ながら**次を通しておく。

1. 本番のダンプを取る
2. 空のデータベースへ戻す
3. `DATABASE_URL` をそこへ向けて `python manage.py migrate --check` が通る
4. `/health/ready` が 200 を返す
5. 管理画面で、学習セッションの件数が元と合っている

通ったら、通った日付をこの節に書き足す。
書いていない期間が長いほど、その手順は信用できない。

- 最後に復旧を通した日: **（未実施 — 公開前に必ず一度）**

## 2. 管理画面の守り

### なぜ要るか

管理画面の向こうには、実証実験で集めた**全学習者の記録**がある。
いま間にあるのは合言葉ひとつだけで、しかも `/admin/` という
誰でも知っている場所に出ている。自動化された総当たりは、
公開した翌日にはそこを叩き始める。

合言葉が強ければよい、とは言い切れない。使い回された合言葉が
どこか別のサービスから漏れる経路は、こちらでは塞げないため。
そこで守りを2枚にする。

### 1) 場所を変える — `DJANGO_ADMIN_PATH`

| キー | 既定 | 例 |
|---|---|---|
| `DJANGO_ADMIN_PATH` | `admin/` | `kanri-7f3a/` |

先頭・末尾の `/` は付けても付けなくてもよい（どちらでも同じ場所になる）。
空にすると既定へ戻る。

これは鍵ではない。当てられれば終わりなので、**単独では使わない**。
効くのは「`/admin/` だけを狙う自動化された総当たりに見つからない」ところまで。

> **Vercel では `vercel.json` の `rewrites` にも同じパスを足すこと。**
> いまは `/admin/(.*)` だけを backend へ振り分けているので、
> パスを変えると画面側へ流れて 404 になる。動かないので気づけるが、
> 「変えたら管理画面が消えた」と焦る前にここを見る。

### 2) 入れる接続元を絞る — `DJANGO_ADMIN_ALLOWED_IPS`

| キー | 既定 | 例 |
|---|---|---|
| `DJANGO_ADMIN_ALLOWED_IPS` | （空 = 制限しない） | `203.0.113.10,198.51.100.4` |

カンマ区切り。**空のあいだは何も制限しない。**
既定を「制限あり」にすると、設定を知らない人の手元で管理画面が
いきなり消えるので、締め出すのは締め出すと決めたときだけにしてある。

当たったときに返すのは **404**。403 だと「ここに管理画面はあるが
あなたは入れない」と教えることになり、1) で場所を変えた意味が消える。

前段にロードバランサ（Vercel も含む）があるときは
`TRUST_FORWARDED_FOR=true` も必要。入れないと、接続元がバランサに見えて
誰も入れなくなる。逆に、直接公開している状態で `true` にすると
ヘッダを詐称して絞りを抜けられるので、**配下に置いたときだけ** `true`。

自分の接続元は次で分かる。

```bash
curl -s https://api.ipify.org
```

固定 IP でない回線（家庭用の多く）だと、割り当てが変わるたびに
自分が締め出される。その場合は 1) の場所変更を主にして、
入る必要が出たときだけ 2) を一時的に足す運用にする。

### 3) 触った記録を残す — `AuditLog`

場所を変えて接続元を絞っても、**入ったあとに何をしたかは残らない**。
管理画面の向こうには全学習者の記録があるので、そこは埋めておく。

Django が標準で持つ `LogEntry` では足りない。あれは追加・変更・削除
しか残さず、**見ただけ**が抜けている。ここで一番起きてほしくないのは
書き換えではなく、記録を意味もなく読んでいくことなので、
そこが抜けていては見張る意味が薄い。

残るのは次のとき。

| いつ | `action` |
|---|---|
| 学習者の記録を管理画面で開いた（一覧・1件とも） | `admin_view` |
| 管理画面で書き換えた | `admin_change` |
| 管理画面で消した | `admin_delete` |
| 本人が学習データを消した | `self_data_delete` |
| 本人がアカウントを消した | `self_account_delete` |
| 定期実行で保存期間切れを消した | `retention_prune` |

教材（`catalog`）を開いても残らない。教材は誰のものでもないので、
全部を対象にすると教材を直すたびに記録が増え、肝心の1件が埋もれる。

**中身は残さない。** 誰の記録を開いたかまでで、そこに何が書いてあったかは
残さない。監査のための記録が、それ自体2つ目の個人情報の山になっては
本末転倒になる。メールアドレスも入れず、人を指すときは `user_id` を使う。

管理画面からは**読むだけ**。触った記録を触った人が消せるなら、
記録が無いのと変わらない（追加・変更・削除の口を全部塞いである）。

保持は既定365日（`AUDIT_LOG_RETENTION_DAYS`）。ゲストの学習データの30日より
長く取ってあるのは、触られたことに気づくのがたいていずっとあとになるため。
同じ物差しで切ると、問い合わせが来た時点で調べる記録がもう無い。

## 3. 古い記録の定期削除（`prune_data`）

### なぜ要るか

プライバシーポリシーには「登録なしで使った場合の記録は、
最後の利用から30日で削除します」と書いてある。
**書いてあるのに動いていなければ、それは事実と違う記載になる。**
消し忘れた記録が残っている状態は、書いていない場合より悪い。

消す中身は `backend/apps/lessons/management/commands/prune_data.py` にある
（登録していない人の記録・古い試行回数・日次カウンタ）。
登録した人の記録と教材そのものは消えない。

Vercel には常駐するプロセスも cron の置き場も無い（要求が来たときだけ
関数が動く）。代わりに **Vercel Cron** が決めた時刻に URL を叩くので、
HTTP から叩ける入り口を用意してある。

```
POST /api/v1/maintenance/prune/
Authorization: Bearer <CRON_SECRET>
```

### 手順

**1. 合言葉を作る**

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

**2. Vercel の環境変数に `CRON_SECRET` として入れる**

Project → Settings → Environment Variables → **Production**。

この名前にしてあるのは偶然ではない。Vercel は `CRON_SECRET` が入っていると、
Cron からの要求に `Authorization: Bearer <CRON_SECRET>` を**自分で付ける**。
別名にすると、自分でヘッダを足す仕組みを書く羽目になる。

> **`CRON_SECRET` が空のあいだ、この入り口は 404 で存在しない。**
> 「空なら素通り」にすると、入れ忘れた配置で
> 「誰でも全データを消せる URL」が開く。入れ忘れは必ず起きるので、
> 起きたときに安全な側へ倒してある。

**3. `vercel.json` の `crons` を確認する**

```json
"crons": [
  { "path": "/api/v1/maintenance/prune/", "schedule": "0 18 * * *" }
]
```

時刻は **UTC**。`0 18 * * *` は日本時間の翌 03:00 にあたる。
学習者がいちばん少ない時間に寄せてある。

**4. 動いたか確かめる**

初回は待たずに、自分で叩いて確かめる。

```bash
curl -i -X POST \
  -H "Authorization: Bearer $CRON_SECRET" \
  https://<プロジェクト>.vercel.app/api/v1/maintenance/prune/
```

返ってくるのは消した件数。

```json
{"status":"ok","days":180,"cutoff":"2026-02-20",
 "deleted":{"学習セッション":3,"診断の回答":1,"身につけたこと":0,
            "試行回数":12,"AI実行回数":40},
 "deleted_total":56}
```

件数を返すようにしてあるのは、**動いていることを外から確かめるため**。
何も返さない作りだと、空振りし続けていても誰も気づけない。

期待どおりの応答:

| 状況 | 返り |
|---|---|
| `CRON_SECRET` 未設定 | `404`（入り口が存在しない） |
| ヘッダ無し・合言葉違い | `401` |
| 正しい合言葉 | `200` と件数 |

**5. その後は月に一度、動いた形跡を見る**

Vercel の Project → **Cron Jobs** に前回の実行時刻と結果が出る。
ログ（Observability → Logs）で `cron.prune.done` を検索してもよい。
記録が途切れていたら、定期実行は止まっている。

手元やサーバーの中から直接動かすこともできる。何が消えるかを
先に見たいときは、必ず `--dry-run` から。

```bash
python manage.py prune_data --dry-run
python manage.py prune_data
```

## 4. メール送信の設定と到達性

### なぜ要るか

このアプリがメールを送るのは3通だけ（メールアドレスの確認 /
パスワードの再設定 / 登録完了のお知らせ）。少ないが、**どれも
届かないと先へ進めない種類**のもので、代わりの手段が無い。

そして届かないときの困り方が独特で、送った側は成功したように見える。
受け取る側の迷惑メール箱に入っているだけなので、エラーはどこにも出ない。
気づくのは「確認メールが来ない」という問い合わせが来たときになる。

### 送り口

本番では `EMAIL_BACKEND` を smtp にし、`EMAIL_HOST` と
`DEFAULT_FROM_EMAIL` を必ず入れる。入れないと**起動時に止まる**
（`backend/config/settings.py` の関門）。送れないまま登録を開くと、
確認も再設定もできない人がそのまま溜まっていくため、
起動させないほうがましだという判断。

送る先は Resend / SendGrid / Amazon SES など。自前の SMTP は勧めない。
新しい IP からの送信は、まず信用されないところから始まる。

### SPF / DKIM / DMARC — なぜ設定しないと届かないか

受け取り側（Gmail など）は、差出人のドメインを名乗る**誰でも**が
メールを送れることを知っている。だから「このドメインを名乗ってよい
送信元か」を、ドメインの DNS レコードで確かめる。

| レコード | 何を言っているか | 無いとどうなるか |
|---|---|---|
| **SPF** | このドメインからのメールは、この送信サーバーが出す | 名乗りが裏付けられず、迷惑メール寄りに判定される |
| **DKIM** | 本文とヘッダに、ドメインの秘密鍵で署名してある | 途中で書き換えられていないことを示せない |
| **DMARC** | SPF / DKIM が合わなかったときにどう扱ってほしいか | 判定が受信側任せになる。報告も受け取れない |

2024年以降、Gmail と Yahoo! は一定量以上の送信に対して
これらを**要件**として扱っている。設定しないと、届かないのではなく
**迷惑メール箱へ静かに入る**。これがいちばん厄介で、
こちらにも学習者にも何のエラーも出ない。

設定は送信サービス（Resend など）が出す値を、ドメインの DNS へ
そのまま登録するだけ。DMARC は監視から始めてよい。

```
_dmarc.example.com  TXT  "v=DMARC1; p=none; rua=mailto:dmarc@example.com"
```

`p=none`（何もしないが報告はもらう）で1〜2週間ようすを見て、
報告に問題が無ければ `p=quarantine` へ上げる。

### 届いているかの確かめ方

公開前に一度、**自分以外の宛先**へ実際に送って確かめる。
自分のドメイン宛は通りやすいので、確認にならない。

1. Gmail / Yahoo! / 会社のアドレスの3つへ、登録から確認メールを送る
2. 受信箱に入るか（迷惑メール箱ではなく）
3. Gmail なら「メッセージのソースを表示」で
   SPF / DKIM / DMARC がすべて `PASS` になっているか
4. メール内のリンクを開いて、確認が完了するか
   （`FRONTEND_URL` が間違っていると、ここで初めて分かる）

## 5. AI 費用の見張り

### なぜ要るか

AI の利用料は、使われた分だけ後から請求される。
上限を置かないと、悪意が無くても跳ねる。

- Cookie を消せば新しい学習者として数え直せる（`learner_key` は Cookie）
- 誰かが自動化して叩けば、1日で月の想定を超えられる
- こちら側の不具合（再試行の無限ループなど）でも同じことが起きる

止め方は2段。**こちら側の上限**と、**提供元の上限**。
片方だけでは足りない。こちら側の上限は、こちら側の不具合では効かないため。

### 提供元の上限（最後の砦）

こちらのコードが何をしようと、ここで止まる。必ず入れる。

- **OpenAI**: Platform → Settings → **Limits** →
  `Budget limit`（そこで止まる）と `Notification threshold`（メールが来る）。
  月の予算の 8割 で通知、10割 で停止にしておく
- **Anthropic**: Console → **Billing → Usage limits** で同じ設定。
  加えて、鍵ごとに上限を分けられる（`Workspaces`）ので、
  実証実験用の鍵を分けておくと、そこから溢れない

自動チャージ（auto recharge）は**切る**。入れたままだと、
上限に当たっても勝手に積み増されて止まらない。

### こちら側の上限

`backend/config/settings.py` に3段ある。詳しくは
`backend/apps/lessons/services/quota.py`。

| 設定 | 既定 | 何を止めるか |
|---|---|---|
| `MAX_ATTEMPTS_PER_SESSION` | 10 | 1回の練習での試行錯誤の範囲（体験の設計） |
| `AI_DAILY_REQUEST_LIMIT_GUEST` | 10 | 登録前の人の1日あたり |
| `AI_DAILY_REQUEST_LIMIT_USER` | 50 | 登録した人の1日あたり |
| `AI_RUNS_PER_IP_PER_DAY` | 100 | 1つの接続元からの使いすぎ（悪用対策） |
| `AI_RUNS_PER_DAY` | 2000 | 全体。想定外が起きても請求が跳ねないための安全弁 |

`AI_MAX_OUTPUT_TOKENS`（既定 600）と `AI_MAX_INPUT_CHARACTERS`（既定 5000）は
1回あたりの単価を決める。回数の上限と掛け算で、1日の最大額が見積もれる。

### `AiUsageCounter` で何が見えるか

管理画面 → **AI実行回数** に、日付ごとの実行回数が並ぶ。

- **対象が「全体」の行** … その日にアプリ全体で AI を呼んだ回数。
  提供元の請求と突き合わせるのはこの数。合わなければ、
  数えていない経路（再試行など）があるということ
- **対象が「接続元 …」の行** … 接続元ごとの回数。
  1つだけ突出していたら、自動化されて叩かれている疑い。
  `AI_RUNS_PER_IP_PER_DAY` を下げるか、その接続元を止める

保存しているのは IP そのものではなく HMAC の値なので、
元の IP は復元できない（憲章 原則 VI）。「同じ相手か」の判定にだけ使える。

管理画面の **検証サマリー** にも、その日の全体の実行回数が出る。
毎日ここを見るなら、跳ね上がりはその日のうちに見つかる。

古い行は `prune_data`（上の 3）が片付ける。

## 6. 何かおかしいとき、まずどこを見るか

上から順に。**下へ行くほど時間がかかる**ので、順番を飛ばさない。

### 1) `/health/live` — プロセスが生きているか

```bash
curl -i https://<プロジェクト>.vercel.app/health/live
```

`{"status":"ok"}` が返れば、アプリ自体は動いている。
外は何も見ないので、DB が落ちていてもここは 200 を返す。
**返らない**なら、アプリが起動していない（設定の関門で止まっている
可能性が高い。次のログを見る）。

### 2) `/health/ready` — 実際に捌けるか

```bash
curl -s https://<プロジェクト>.vercel.app/health/ready | python3 -m json.tool
```

```json
{"status":"unavailable",
 "checks":{"database":false,"migrations":true,"ai":true,"email":true},
 "ai_provider":"openai"}
```

`false` になっている項目が、そのまま原因の場所。

| 項目 | `false` のとき見るところ |
|---|---|
| `database` | Neon が起きているか（無料プランは休止する）、`DATABASE_URL`（**接続できるか**だけを見る） |
| `migrations` | 本番DBへ `migrate` を当て忘れている（**接続はできるが、表が足りない**。下の 7 を参照） |
| `ai` | `AI_PROVIDER` に対応する鍵が入っているか |
| `email` | `EMAIL_HOST` / `DEFAULT_FROM_EMAIL` |

`database` と `migrations` は別の軸で、**`database:true` は「migrate 済み」を意味しない**。
実際に、本番PostgreSQLへ migrate を当て忘れたまま配置し、`database:true` のまま
`/api/v1/ai/generate/` が `relation "catalog_lesson" does not exist` で 500 になる事故が起きた
（`apps/health/views.py` の `_migrations_ok()` はこれを検知するために足した）。

どれが駄目かまでは言うが、理由の詳細は出さない
（接続先や鍵の有無が分かると、攻撃の下調べに使えるため）。
詳細はログで見る。

### 3) Vercel のログ

Project → **Observability → Logs**（配置ごとなら Deployment → Runtime Logs）。

探すもの:

| 手がかり | 意味 |
|---|---|
| `ImproperlyConfigured` | 本番の関門で止まっている。足りない環境変数が本文に出る |
| `admin.blocked` | `DJANGO_ADMIN_ALLOWED_IPS` で自分を締め出している |
| `cron.prune.done` | 定期削除が動いた記録。途切れていたら止まっている |
| `cron.prune.unauthorized` | `CRON_SECRET` が合っていない |
| `auth.session.expired` | ログインの上限で切れた（不具合ではない） |
| `AI_SERVICE_NOT_CONFIGURED` | 鍵が入っていない、または名前が違う |

`SENTRY_DSN` を入れてあれば、例外は Sentry にも集まる
（本文は送らない設定にしてある）。

### 4) それでも分からないとき

- **配置し直す前に**、直前の配置との差分を見る。Vercel は
  1つ前の配置へ即座に戻せる（Deployments → 前の配置 → Promote）。
  原因を探すより先に、まず戻して学習者を通す
- 環境変数を変えたなら、**再配置しないと反映されない**。
  「設定は直したのに直らない」の大半はこれ
- DB を触る前に、必ず 1 のバックアップを取る。
  調べているうちに壊すことがある

## 7. Production migration の自動化

### なぜ要るか

`migrate` は Vercel の build ステップに**意図して入れていない**
（`backend/build.py` 参照）。Preview 環境も本番と同じ `DATABASE_URL` を
向いている構成のことが多く、デプロイのたびに（Preview も含めて）
勝手に migrate が走ると事故る。だから今までは「手元から Neon へ直接
繋いで実行する」（[deploy-vercel.md](./deploy-vercel.md) の 4）を、
配置のたびに**手で**やる前提だった。

手でやる前提のものは、いつか忘れる。実際に一度、本番へ push した
あとに migrate を当て忘れ、`/health/ready` は緑のまま
`relation "catalog_lesson" does not exist` で AI 生成が全滅する事故が
起きた（6 の表にある `migrations` の項目は、この事故を機に足した）。

### 仕組み

`.github/workflows/release-migrate.yml`。**`main` への push だけ**で動く
（PR やプレビューでは動かない）。

```
push: main
  → PRODUCTION_DATABASE_URL が空/postgresでなければ、ここで止める
  → showmigrations --plan（当てる前にログへ残す）
  → migrate --noinput
  → seed_catalog（何度実行しても同じ結果になる）
  → migrate --check（当て漏れが無いことを、ジョブ自身が確かめる）
```

GitHub の **Environment**（`production`）に紐付けてある。これにより:

- **`PRODUCTION_DATABASE_URL` は `production` Environment 専用の secret**
  として登録する（Settings → Environments → New environment →
  `production` → Environment secrets）。リポジトリ共通の Secrets に
  置くと、他のワークフロー（PR 起因のものなど）からも読めてしまう
- 同じ画面で **Required reviewers** を設定すると、migrate が実行される
  前に人の承認待ちになる。destructive な migration（列を落とす、
  等）が紛れていないかを、当てる前に一度人が見る場所として使える
  （**現状は未設定。運用を始める前に設定すること**）

secret が空のまま実行されると、`config/settings.py` の分岐で
静かに SQLite（Actions ランナー上の使い捨てファイル）へ落ち、
何もしないまま緑で終わる——これがいちばん危ない失敗なので、
ワークフローの最初の関門でここを止めている（空・`sqlite://` 等を弾く）。

並列に push が続いても、`concurrency` で migrate 自体は1本ずつ直列に
処理する。

### 初回だけ、手で

このワークフローは「次に `main` へ push されたとき」から効く。
**いま起きている `relation "catalog_lesson" does not exist` そのものは、
このワークフローを足しただけでは直らない**（`main` への次の push を
待つか、Actions タブから手動で re-run する必要がある）。今すぐ直すには
[deploy-vercel.md](./deploy-vercel.md) の 4 の手順を先に1回、手で実行する。

### この仕組みが検知しないもの

- `migrate` 自体が失敗する壊れた migration（それはこのジョブが赤くなって教える）
- 本番データに対して**意味的に**危険な migration（列の削除など）。
  ここは Required reviewers による人の目が最後の砦
