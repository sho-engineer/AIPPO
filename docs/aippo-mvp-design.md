## 市場に出すための追加分

MVP の完成条件を満たしたあと、「公開したら困ること」を先に潰した分。

### AI利用料の暴走を止める（最大の実害リスク）

`learner_key` は Cookie なので、消せばセッション上限を回避して
1人でいくらでもAIを実行できてしまう。**公開した瞬間に利用料が青天井になる。**

三段構えにした。

| 段 | 設定 | 目的 |
| --- | --- | --- |
| セッション単位 | `MAX_ATTEMPTS_PER_SESSION`（10） | 1回の練習での試行錯誤の範囲（体験の設計） |
| 接続元単位・1日 | `AI_RUNS_PER_IP_PER_DAY`（100） | 1人が使いすぎるのを止める（悪用対策） |
| 全体・1日 | `AI_RUNS_PER_DAY`（2000） | 想定外でも請求が跳ねない（最後の安全弁） |

**IPアドレスは保存しない。** `SECRET_KEY` を鍵にした HMAC だけを持つ（憲章 原則 VI）。
上限に達してもポーは固定ヒントを返し、レッスンは止まらない（憲章 原則 III）。

数え上げは条件付き **UPDATE 1文**で行う。
「読んでから書く」形にすると行を掴んだまま待つことになり、
同時アクセスで詰まって 500 になる（SQLite では特に顕著）。

### 本番設定

- 開発用の鍵や未設定の `ALLOWED_HOSTS` のまま本番起動しようとしたら**動き出す前に落とす**
- HTTPS・HSTS・Cookie・クリックジャッキング・本文サイズの上限
- `DATABASE_URL` による PostgreSQL 切り替え
- 死活監視を `health/live`（何も見ない／再起動の判断）と
  `health/ready`（DB・AIの設定・メールの設定を見る／振り分けの判断）に分離
  （`healthz` / `readyz` は旧名として残してある）
- `manage.py check --deploy` が無警告

### 体感速度

待ち時間の99%以上がAIの応答待ちなので、言語や実装の速さではなく
**書けたところから見せる**ことが効く。
`POST /api/lessons/rewrite-text/stream/`（Server-Sent Events）を追加した。
使えない環境では画面が黙って通常の生成へ倒れる。

### 実証実験のデータを見る手段

管理画面が入っておらず、集めたログを誰も見られない状態だった。
完了率・離脱した画面・AI利用料・アンケート集計を1画面にまとめた
（`/admin/lessons/verificationsummary/`）。学習者の本文は読み取り専用で、集計画面には出さない。

### 実装されていなかった箇所（洗い出しと対処）

固定文言・モデル・イベント種別の使用状況を突き合わせて見つけたもの。

| 箇所 | 状態だったもの | 対処 |
| --- | --- | --- |
| **AI活用診断の回答** | UIで集めているが、どこにも保存していなかった。`LearnerProfile` はモデルとマイグレーションだけで API が無い | `POST /api/profile/` を追加。管理画面に「誰が来て、誰が完走したか」を経験別に出す |
| **安全上の注意（§15）** | 「医療・法律・お金は専門家にも確認」が画面に一度も出ていない。「個人情報を入れない」も最初の入力画面に出ていない | `SafetyNote` を作り、文章を書く場所と AI の回答を読む場所の両方に出す |
| **離脱の記録** | `lesson_abandoned` が一度も送られておらず、最後にいた画面からしか推測できなかった | 画面を離れるときに送る（`keepalive` 付き。付けないと送信が打ち切られる） |
| 例文で試す導線の文言 | コンポーネントに直書き（§17 違反） | `BUTTONS.useSample` へ集約 |

完了率だけでは、AIを使ったことがない人が離脱しているのか、
ふだん使う人が物足りなくて離脱しているのかを区別できない。
診断の保存は、その区別をつけるために要る。

### 配色とキャラクター

白と黒だけの画面は、対象（AIに不安がある初心者）に対して硬すぎた。
「自分にもできそう」と思えるかがそのまま着手率になるため、
やわらかい配色に作り替えた。

色は **`frontend/tailwind.config.js` に名前で定義**し、
コンポーネントに生の色コードを書かない。
ブランド色を変えたくなったときに直す場所を1か所にするため。

| 名前 | 用途 |
| --- | --- |
| `canvas` | 画面の下地。真っ白より、ほんのり色を入れたほうが緊張しない |
| `brand` | 主役の色。ボタンと進み具合 |
| `joy` | できた・進んだ |
| `caution` | 気をつけて（赤ほど強くしない） |
| `ink` / `ink-muted` | 文字。真っ黒より、わずかに紫を含ませて背景となじませる |

**やわらかくしても読みやすさは落とさない。**
本文の色は背景に対して 4.5:1 以上を保っており、
`e2e/a11y.spec.ts` が自動で検査する（配色を変えるとここが落ちる）。

#### 書体

**丸ゴシック（Zen Maru Gothic）**を使う。
日本語で「親しみやすさ」を出す手段として、色よりも効く。
角ゴシックのままだと、配色を変えても事務書類の印象が残る。

文字は既定より一段大きくし、行間も広げた（`tailwind.config.js` の `fontSize`）。
12px の文字が並ぶと「細かい注意書き」に見えて、それだけで身構えさせる。
対象は年齢層も幅広いので、読みやすさを優先する。

日本語のフォントは1ウェイトで 1.4MB あり、そのまま読み込ませると
スマートフォンで最初に開く人が 3MB 近く待たされる。
`scripts/build-fonts.py` が `unicode-range` で16個に分けており、
ブラウザは**画面に出た文字を含む断片だけ**を取りに行く。

| | 大きさ |
| --- | --- |
| 全部 | 約 3.2MB |
| **最初の1画面で実際に要る分** | **約 161KB** |

アプリ自身の文言に出る文字だけを集めた断片を用意し、
`unicode-range` が重なったときは後に書いた指定が勝つ性質を使って
**CSS の最後**に置いてある。順番を入れ替えるとこの最適化は効かなくなる。

`e2e/a11y.spec.ts` が「丸ゴシックが実際に使われているか」と
「最初の1画面のフォントが重すぎないか」を検査する。

#### キャラクター

ポーの絵は**支給されたキャラクター画像**を使う（白い体に水色、頭にアンテナ）。
`scripts/build-poe.py` が6表情ぶんを整えている。

やっていることは3つ。

1. 透明な余白を切り落とす
2. **体の大きさと足元の位置をそろえる**
3. WebP で書き出す（1枚 33〜39KB）

2 が肝心。元の絵は1枚ずつ大きさも位置も違うので、そのまま並べると
表情が変わるたびにポーが飛び跳ねて見える。
「？」や吹き出しのような浮いている飾りは体から離れた別のかたまりなので、
いちばん大きなかたまり（＝体）だけを見つけて基準にしている。

6表情とも支給画像がある（電球・！の標識・紙吹雪まで揃っている）。
手を振っている絵はトップの主役として別に持つ（`brand/poe-wave.webp`）。

飾りに使う絵は表情とは別の扱いにしてある。
表情は6枚を同じ正方形へ収める必要があるが、飾りは1枚で完結するので
**余白を切り詰める**。同じ枠に収めると3割が透明な余白になり、
大きく見せたい場所で絵が小さくしか出せない。

元絵は四隅まで透明ではなく、ごく薄い光が敷いてある。
そのままでは (a) 濃い色の面に載せたとき四角い靄として見え、
(b) 余白を切り詰めようとしても元の大きさが返ってくる。
書き出す前に、この薄い光だけを透明にしている（`clear_haze`）。

**画面の配色はこのキャラクターから取っている。**
主役の色はポーの青、文字色はポーの輪郭の紺、下地はポーの白い体になじむ薄い青。
ただし白文字を載せるボタンは、明るい水色のままでは薄すぎるため、
コントラストが 4.5 以上になるところまで濃くしてある。

### 「出来合いのひな形」に見えないようにする

配色と書体を直しても、**構成が定型のまま**だと作り物に見える。
やめたのは次の3つ。

| やめたこと | なぜ | 代わりに |
| --- | --- | --- |
| 文字間を空けた「A I P P O」でブランドを表す | それはロゴが無い画面の見た目であって、ブランドの顔ではない | 支給されたロゴを使う（`BrandLogo`） |
| 薄い下地に白い角丸カードを並べる | どの面も同じ重みで、視線の行き先が無い | トップは**ゲームのタイトル画面**にする（次項） |
| 番号つきカードを3枚横に並べる | 手順を「並べただけ」で、進む感じが出ない | **すごろくの盤面**にする。右へ行くほど高い位置に置き、点線でつなぐ。名前の由来が「AI＋一歩」なので、登っていく形そのものを見せる |

おすすめ画面も、いま試せるものとこれから作るものを**同じ見た目にしない**。
同じ重みで並べると、どれを選べばよいか分からなくなる（憲章 原則 I）。

> 濃い面の上で白を薄める（`text-white/90`）と、読みやすさの基準を割る。
> `e2e/a11y.spec.ts` が実際にこれを検出したので、白のまま使っている。

### トップ画面をタイトル画面にする

配色を整え、ロゴを入れ、構成を直しても、なお「単調」だった。
残っていた理由は**画面が一枚の平らな板に見えていたこと**で、直し方は2つ。

#### 1. 層に分ける（奥行き）

タイトル画面の背景を4層にした（`TitleBackdrop`）。

| 層 | 中身 | 速さ |
| --- | --- | --- |
| 空 | グラデーション | 動かない |
| 遠景 | 強くぼかした大きな面 3つ | 19秒でゆっくり |
| 丘 | ポーが立つ地面。2枚重ね | 動かない |
| 手前 | 泡 8つ・きらめき 4つ | 13〜25秒でばらばら |

決め事が3つある。

- **速さを層ごとに変える**。全部同じ速さで動かすと、一枚の板が揺れて見えるだけ
- **奥は薄く、手前は濃く**。逆にすると前後が入れ替わって見える
- **左右のはみ出し方をずらす**。丘を左右対称に置くと、そこだけで作り置きの見た目に戻る

泡は位置・大きさ・速さ・遅れをわざと不揃いにしてある。
等間隔に並べると模様になり、「機械が置いた」感じがかえって強く出る。
遅れは**負の値**を入れて途中から始める。開いた瞬間に全部が下から
一斉に上がると、演出が始まったことがばれる。

#### 2. 動かす（生きている感じ）

動かす目的は賑やかしではなく、次の3つに限っている。

| 目的 | 何をしているか |
| --- | --- |
| 生きている感じを出す | ポーが呼吸するように浮く（`float`）。**浮いた分だけ足元の影が縮む**（`float-shadow`） |
| 押せる場所を教える | 「はじめる」から輪が広がる（`halo`） |
| 順番を教える | ロゴ → 読み → キャッチコピー → ポー → ボタン の順に現れる |

動きは全部 CSS で、キーフレームは `tailwind.config.js` に置いてある。
ライブラリを足すほどの見返りが無く、まとめて止められる形が扱いやすい。

実装で引っかかった点が2つ。

- **登場と待機は別の要素に分ける**。同じ要素に両方書くと、後から書いたほうだけが効く
- **登場には `animation-fill-mode: both` を付ける**。付けないと、遅らせて出す要素が最初の一瞬だけ元の位置に見える

#### 動きが苦手な人には出さない

動きで気分が悪くなる人がいる。端末が `prefers-reduced-motion: reduce` の
ときは、`index.css` で全部の動きを一瞬で終わらせる。

`animation: none` にはしない。それだと遅らせて出している要素が
**現れないまま消える**。`e2e/a11y.spec.ts` が、この設定で
（a）動いているものが1つも無いこと（b）それでも「はじめる」が見えていること
の両方を検査する。

#### 1画面に収める

タイトル画面と名乗る以上、スクロールしないと始められないのでは形にならない。
`e2e/a11y.spec.ts` が、ロゴ・ポー・「はじめる」の3つが
最初の1画面に収まっていることを検査する。

中身は縦の**真ん中**へ置いている。下端へ寄せると、
画面が縦に長い端末でボタンが枠の外へ出る（実際に出た）。

### UI・UX の手直し

画面を実際に書き出して（`e2e/screenshots.spec.ts`）確認したもの。

| 症状 | 直し方 |
| --- | --- |
| **ポーの吹き出しが画面の右外へはみ出して読めない。ポー自身も見えない** | 吹き出しを必ず縮む指定にした（内容に合わせて広がる指定だと、長い発言であふれる） |
| **狭い画面でポーが縦に伸び、下の選択肢を覆う** | 高さに上限を設けた |
| **穴埋めの薄い文字が選択肢とまったく同じ文字列**（「社外のお客様」「3行くらい」）。もう選ばれていると読めて、そのまま送って怒られる | 「ほかの相手を書く（例：取引先の担当者）」のように、選択肢とは別物と分かる文言へ |
| 進み具合が「3 / 9」の数字だけで、あとどれくらいか掴めない | 進捗バーを追加 |
| **完了画面が行き止まり**。レッスンは1本しかないので、いちばん乗り気になった人の戻り道が無い | 「もう一度はじめから試す」を追加 |

いずれも回帰テストを追加してある
（ポーのはみ出し・覆いは `e2e/a11y.spec.ts` で画面の外に出ないことを実測）。

### 探索テストで見つけた不具合（追加分）

| 症状 | 原因 |
| --- | --- |
| ブラウザからの流し込みが全部 406 で弾かれ、一度も効いていなかった | DRF の内容交渉が `Accept: text/event-stream` を拒否。curl（`*/*`）では通るため気づけない |
| 同時アクセスで 500（database is locked） | 実行回数の数え上げが行を掴んだまま待つ形だった |
| **診断を終えた人にだけ** 500（database is locked） | 診断の保存が `update_or_create`、つまり1つのトランザクションの中で「読んでから書く」形だった。読んだ時点では共有ロックしか持っておらず、書き込みへ昇格しようとして別の接続とかち合うと、待ち時間の設定に関係なくその場で失敗する |
| 文字が薄くて読みにくい（コントラスト 4.42 / 2.35） | `text-neutral-500` `text-neutral-400` を本文に使っていた |
| どこかで例外が出ると真っ白な画面になる | エラー境界が無かった |

### 探索テストで見つかった不具合

スタブではなく本物の Django・DB・Cookie に当てて、実装だけでは気づけない
5件を検出した。いずれも修正済みで、回帰テストを追加してある。

| # | 症状 | 原因 | 対処 |
| --- | --- | --- | --- |
| 1 | 自分の文章で実行すると振り返りへ進めない | `RUN_SUCCEEDED` の行き先が固定だった | `nextStep()` を遷移元に応じて分岐 |
| 2 | ポーの助言が出ない | `dispatch` 直後の `stateRef` を読んでいた | 遷移先を引数で明示 |
| 3 | 接続先ホストのずれで通信が届かない | 既定が `localhost` 固定・CORS 許可も片方だけ | 表示中のホストから導出（`api/config.ts`）＋CORS を両方許可 |
| 4 | ポーの返事を待つ間の操作が黙って捨てられる | 二重送信の錠前が助言の通信まで覆っていた | 生成の完了で解除。追い越された古い返事は捨てる |
| 5 | 進んだ画面が後ろへ引き戻される | 再開の問い合わせが遅れて届き、現在地を上書き | まだ何もしていないときだけ再開を適用 |

加えて、狭い画面でポーが下のボタンのタップを奪っていたため
`pointer-events-none` を付けた（憲章 原則 I）。

## 0. 前提と、明記しておく仮定

### 確認できなかったこと

`sho-engineer/AIPPO` リポジトリを **このセッションからは読めなかった**。
GitHub アクセスが `sho-engineer/tripix` に固定されており、
リポジトリ追加には承認が必要で、非対話セッションでは承認フローを実行できない。

### したがって置いた仮定

| # | 仮定 | 外れた場合の影響 |

### 3.4 設計上の懸念（判断を仰ぎたい点）

いずれも実装は可能。**進め方の推奨と、その理由を添える。**

#### Q-1: AI活用診断を MVP に含めると、レッスン完成が遅れる

> ✅ **確定**: 推奨どおり3問に絞る。`LearnerProfile` を実装済み（MVP使用は3項目）。

概要 §17 は「まず1レッスンを最後まで完成させる」としつつ、
§11 は AI活用診断を必須機能に挙げている。両立させるなら診断は最小構成にすべき。

**推奨**: 診断を **3問の選択式** に絞る（職種 / AI利用経験 / 今いちばん面倒なこと）。
自由入力なし、スコアリングなし、結果は用途3件の静的マッピング。
`LearnerProfile` のフィールドは §14 の6項目すべてを持たせるが、
**MVPで埋めるのは3項目のみ**とし、残りはフェーズ3で追加する。

理由: 診断の精度は「実際に使ってもらった後」でないと検証できない。
先に精度を作り込むと、レッスン完成が遅れるうえ手戻りも大きい。

#### Q-2: 操作ログにユーザー入力の全文を保存するか

> ✅ **確定**: 推奨どおり保存しない。`LearningEvent.input_length` のみ実装済み。

§13 は「入力文字数」を記録項目に挙げつつ、
「入力全文をログへ保存する場合は個人情報・機密情報の扱いに注意する」と補足している。

**推奨**: `LearningEvent` には **本文を保存しない**（文字数のみ）。
本文は `Attempt.user_input` に保持し、こちらへアクセス制限をかける。
ログとコンテンツを分離しておけば、後から「ログだけ長期保管」ができる。

#### Q-3: MVP に `User` モデル（ログイン）が必要か

> ✅ **確定**: 推奨どおり匿名Cookieのみ。`User` は導入していない。

§14 は `User` を挙げているが、§11 の MVP に決済もログイン画面も無い。
初回30分で成果物を作らせる（§5）目標に対し、登録は最初の離脱要因になる。

**推奨**: MVP は **匿名セッションキー（HttpOnly Cookie, 90日）** で識別する。
実装済み（`apps/lessons/middleware.py`）。`LearnerProfile` は
`learner_key` に紐づけ、`User` は導入せず、フェーズ後半で
匿名セッションをアカウントへ引き継げる構造にしておく。

> **追記（Closed Beta）**: その「フェーズ後半」がここ。`User` を追加したが、
> 匿名で始められる性質は変えていない。登録は任意で、入口はレッスン完了画面と
> 設定の2か所だけ。引き継ぎの仕組みは §7.3。

#### Q-4: `hint_level: 3` の「具体例」と 100文字制限が衝突する

> ✅ **確定**: 推奨どおり段階3のみ150文字。Serializer で段階別に切り替え済み。

具体例を提示すると 100文字に収まらない場合がある。

**推奨**: `hint_level` が 3 のときのみ **150文字まで許容** する。
Serializer の上限をレベル別に切り替える。

#### Q-5: `Attempt` と既存 `AiRun` / `TutorFeedback` の関係

> ✅ **確定**: 推奨どおり `Attempt` へ統合済み。`model_name` / `token_usage` も追加。

§14 の `Attempt` は、生成結果とチューターのフィードバックを1レコードに持つ設計。
既存実装は `AiRun`（生成）と `TutorFeedback`（フィードバック）に分けている。

**推奨**: **`Attempt` に統合する**（§14 に合わせる）。
1回のユーザー操作＝1レコードのほうがログ分析が単純になり、
`model_name` / `token_usage` の記録先も明確になる。
`AiRun` / `TutorFeedback` は `Attempt` へマージする。

#### Q-6: バックエンドの言語（Python を続けるか）

> ✅ **確定（2026-08-02）**: **Django のまま実証実験へ進む。**

Python / Django は概要 §12 の指定によるもので、設計時の選択ではない。
「できるだけ Python 以外にしたい・動作が遅くない言語にしたい」という
要望を受けて再検討し、**速度は判断材料にならない**と結論した。

実測（このリポジトリの実装・開発サーバー・`DEBUG=True`）:

| | 実測 |
| --- | --- |
| `POST /api/lessons/rewrite-text/generate/`（スタブ） | 中央値 **23.8 ms** |
| 本番構成（gunicorn・`DEBUG=False`）の目安 | 5〜10 ms |
| 本物の AI 呼び出し（`claude-opus-5` で書き換え） | **2〜6 秒** |

学習者の待ち時間の 99% 以上が AI の応答待ちであり、
言語を替えて 24ms を 3ms にしても体感は変わらない。
**体感に効くのは言語ではなく、応答のストリーミング表示・並行実行・
同条件のキャッシュ**であり、これらは言語を替えずに実装できる。

Python をやめる正当な理由は速度ではなく、**言語が2つあることのコスト**
（型を共有できない・ツールチェーンとテストランナーが2系統・
デプロイ先と CI ジョブが2つ）である。これを解消するなら
TypeScript（Hono + Drizzle + Zod）に寄せるのが唯一妥当な選択肢。
Go は実行速度は最速だが言語が2つのままなので、この利点が得られない。

**書き直しの分岐点はレッスンを2本目に増やすとき**とする。
そこでバックエンドの形が変わるため、移すなら最も安く済む。
移行対象は実装のみで約1,600行（テスト738行を除く）。
なお Django 管理画面は実証実験で学習ログ・アンケートを見るのに使うため、
移行する場合は代替の閲覧手段を先に用意すること。

| 入力の検証（必須・文字数） | ✅ | ✅ | UXのため即時、正しさのためサーバーでも |
| 二重送信の防止 | ✅ | ✅ | §17 |

| 学習セッション・Attempt の永続化 | — | ✅ | |

| 診断結果 → 用途のマッピング | — | ✅ | 後から変えたい |

### 状態の置き場所

```
ブラウザ（useReducer）    現在のステップ・入力途中の値・実行結果の配列
     ↓ ステップ通過ごとに送信
サーバー（DB）            到達ステップ・確定した入力・Attempt・イベント
     ↓ 再訪時に返す
ブラウザ                  RESUME で復元
```

途中の入力はサーバーへ都度送らない（通信を減らし、離脱時の不完全データを避ける）。

## 5. レッスン状態管理の設計

### 5.1 状態と「次の行動」

各状態でユーザーが取る行動は **常に1つだけ** 提示する。

| 状態 | ポーの表情（既定） | 次の行動 |
| --- | --- | --- |
| `INTRO` | `neutral` | 「はじめる」を押す |
| `SELECT_USE_CASE` | `question` | 用途を4つから1つ選ぶ |
| `FIRST_INPUT` | `hint` | 穴埋めを埋めて「AIに送る」 |
| `GENERATING` | `thinking` | 待つ |
| `REVIEW_RESULT` | `neutral` | 結果を確認して「次へ」 |
| `IMPROVE_INPUT` | `question` | 改善の方向を1つ選ぶ |
| `REAL_TASK` | `question` | 自分の文章を入力する |
| `REFLECTION` | `neutral` | 学んだことを確認して「完了する」 |
| `COMPLETE` | `celebrate` | 成果物をコピーする |

### 5.2 遷移表

```
INTRO           --START-->          SELECT_USE_CASE
SELECT_USE_CASE --SELECT_CASE-->    FIRST_INPUT
FIRST_INPUT     --SUBMIT-->         GENERATING
FIRST_INPUT     --BACK-->           SELECT_USE_CASE
GENERATING      --RUN_SUCCEEDED-->  REVIEW_RESULT
GENERATING      --RUN_FAILED-->     returnTo   （入力を保持）
GENERATING      --CANCEL-->         returnTo   （入力を保持）
REVIEW_RESULT   --NEXT-->           IMPROVE_INPUT
REVIEW_RESULT   --BACK-->           FIRST_INPUT
IMPROVE_INPUT   --SUBMIT-->         GENERATING
IMPROVE_INPUT   --NEXT-->           REAL_TASK
REAL_TASK       --SUBMIT-->         GENERATING
REAL_TASK       --NEXT-->           REFLECTION
REFLECTION      --COMPLETE-->       COMPLETE
REFLECTION      --BACK-->           REAL_TASK
```

- **遷移表に無い遷移は無視し、現在の状態を維持する。** 例外を投げない
- `GENERATING` の復帰先は `returnTo`（`FIRST_INPUT` / `IMPROVE_INPUT` / `REAL_TASK`）
- `COMPLETE` は終端

### 5.3 実装

`useReducer` を使う。reducer は2種類のアクションを扱う。

| 種別 | 例 | 挙動 |
| --- | --- | --- |
| 遷移を伴う | `START` / `SUBMIT` / `NEXT` / `BACK` | 遷移表を引く。拒否されたら state をそのまま返す |
| 入力の保持のみ | `SET_FILL_IN` / `SET_REAL_TASK` / `SET_TUTOR` | ステップを変えない |

**`SET_TUTOR` が遷移を伴わないことが重要。**
AI の応答（`action: "next"` など）は表示のヒントであって、遷移の指示ではない。
遷移を実行するのは reducer だけ。

当時の実装は `frontend/src/lesson/` にあり 31 tests で守っていた。
**このディレクトリは削除済み**で、いまは `frontend/src/course/` が同じ役目を負う
（進行は `engine.ts`、状態は `useCourseLesson.ts`）。
「遷移を実行するのはアプリ側だけ」という決まりは変わっていない。

## 6. AIチューターAPIの設計

### 6.1 エンドポイント

```
POST /api/tutor/feedback/
```

**リクエスト**（概要 §13 のとおり）

```json
{
  "lesson_id": "rewrite_text_001",
  "step": "review_input",
  "user_input": "このメールをいい感じにしてください",
  "attempt_count": 1
}
```

| フィールド | 制約 |
| --- | --- |
| `lesson_id` | 最大100文字、既知のIDのみ |
| `step` | 定義済みステップのいずれか |
| `user_input` | 1〜5,000文字 |
| `attempt_count` | 1以上の整数 |

`session_id` はボディに含めない。`learner_key` Cookie からサーバーが解決する。

**レスポンス（200）**

```json
{
  "message": "誰に送るメールなのかを追加してみましょう。",
  "emotion": "hint",
  "action": "retry",
  "hint_level": 1,
  "completed": false
}
```

### 6.2 処理の流れ

```
1. リクエスト検証（Serializer）             不正 → 400（不足内容を返す）
2. attempt_count から hint_level を決める   ← AIの申告は採用しない
3. ステップ別プロンプトを組み立てる
4. AI を呼ぶ（構造化出力でスキーマを拘束）
        タイムアウト 12秒 / リトライ 1回
5. 応答を Serializer で検証                 不適合 → フォールバックへ
6. Attempt / LearningEvent に記録
7. 200 で返す
```

**AI が失敗・タイムアウト・形式逸脱のいずれでも HTTP 200 と固定ヒントを返す。**
エラーをユーザーに見せない。レッスンは必ず前に進む（§17）。

### 6.3 hint_level（AIPPO §8 に合わせる。**要修正 C-1**）

| level | 内容 | 例 |
| --- | --- | --- |
| 0 | ヒントなし | — |
| 1 | 考える方向を示す | 「誰が読む文章かを伝えると回答が変わります」 |
| 2 | 選択肢や穴埋め形式を示す | 「【誰向け】に【どんな表現】で、の形で書いてみましょう」 |
| 3 | 具体例を示す | 「例:『社外のお客様向けに、丁寧に、3行で』」 |

`attempt_count` → `hint_level` は `min(attempt_count, 3)`。
**1回目で正解そのものを提示しない。**

### 6.4 AI文章生成API（新規 N-3）

```
POST /api/lessons/rewrite-text/generate/
```

```json
{ "original_text": "入力文章", "audience": "上司", "tone": "丁寧", "length": "短め" }
```

- タイムアウト 30秒、**リトライなし**（待ち時間が倍増するため）
- 同一内容の二重送信は拒否
- `Attempt` に `model_name` / `token_usage` を記録（§17）

### 6.5 プロバイダ抽象

```
views.py → services/generation.py → AiProvider（Protocol）
                                       ├── AnthropicProvider   実装済み
                                       ├── StubProvider        実装済み
                                       ├── OpenAIProvider      将来
                                       └── GoogleProvider      将来
```

プロバイダ固有の型・SDK をビュー層へ漏らさない。
`AI_PROVIDER=mock` のままレッスンを完走できることを統合テストで担保する（`stub` は同じものの旧名）。

### 6.6 AIへ送るデータの範囲

送るもの: システムプロンプト（固定）、`user_input`、`hint_level`。
送らないもの: `learner_key`、`session_id`、Cookie、IPアドレス、会話履歴、他レッスンの入力。

### 6.7 システムプロンプト（§15 準拠、安全ルール込み — 新規 N-6）

```
あなたは、AI初心者向けハンズオン学習アプリ「AIPPO」の
AIチューター「ポー」です。
対象者は、AIに興味はありますが、
何に使えばよいか分からない非IT人材です。

役割:
- ユーザーを否定しない
- 専門用語を使わない
- 一度に一つだけ改善点を伝える
- 正解をすぐに出しすぎない
- 最初に良かった点を一つ伝える
- 次に行う操作を明確にする
- 100文字以内を基本とする
- 子ども扱いしない
- 明るいが、テンションを上げすぎない

安全ルール:
- 個人情報や機密情報が含まれる可能性がある場合は注意する
- AIの回答を事実として断定しない
- 数字、日付、固有名詞は確認するよう案内する
- 医療、法律、金融などの重要判断は専門家への確認を案内する

指定されたJSON形式だけを返す。
```

これに「現在のレッスン」「現在の段階」「評価項目」「ヒントの段階」を差し込む。

### 7.3 ゲストの記録の引き継ぎ（Closed Beta で追加）

登録でやるのは **`learner_key` が誰のものかを記録すること** だけ。
学習の記録（`LearningSession` / `Attempt` / `LearningEvent` / `SkillProgress` /
`LearnerProfile`）は `learner_key` に紐づいたまま動かさない。

```
LearnerIdentity: learner_key ──→ user
```

この形にした理由。

- **冪等になる。** 二度実行しても結びつきは1つ。登録直後の再読み込みや、
  通信が切れての押し直しは普通に起きる。そのたびに記録が増えると、
  「自分の課題で試した回数」のような数え上げが狂う
- **端末が増えても同じ形で足せる。** 別端末は別の `learner_key` を持つので、
  ログイン時にその鍵も同じ人へ結びつければよい。読むときは
  `learner_keys_for(user)` で「その人の鍵ぜんぶ」を引く
- **記録を書き換えないので、途中で失敗しても壊れない**

同じ端末を2人が順に使ったときは、あとの人へ前の人の記録を渡さない
（`claim_guest_data` は他人の鍵を奪わない）。混ざるほうが困る。

読み書きの範囲は `apps/accounts/scope.py` に1か所へまとめてある。

| | 範囲 |
| --- | --- |
| 読む | その人が読んでよい鍵ぜんぶ（未ログインならいまの端末だけ） |
| 書く | いつもいまの端末の鍵 |

書き込みを「代表の鍵」へ寄せない。寄せると、結びつけに失敗した端末の
記録が迷子になる。読むときはいまの端末の鍵を必ず含めるので、登録直後の
一瞬に、自分で作ったばかりの記録が消えたようには見えない。

引き継ぎに失敗しても **登録そのものは成功させる**。ここで登録ごと
失敗扱いにすると、もう一度登録しようとして「そのメールアドレスは
使われています」に当たり、そこで詰む。応答に `retryable: true` を入れ、
次のログインでやり直す。

### 7.4 個人情報の扱い

- 本文が入るのは `Attempt.user_input` / `generated_output` と
  `LearningSession.real_task_text` の3か所のみ
- `LearningEvent` は文字数のみ
- ログ・エラートラッキングへ本文を出力しない
- 外部AIプロバイダへ送るのは最小限のフィールドのみ
- パスワードはハッシュのみ。メール本文にも応答にも入れない
- ログイン状態はセッション Cookie（HttpOnly / Secure / SameSite）だけで持ち、
  合言葉を localStorage へ置かない
